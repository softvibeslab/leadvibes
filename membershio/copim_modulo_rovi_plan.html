Plan de producto · COPIM como módulo real

Cómo dejar de mostrar COPIM como demo y convertirlo en un módulo nuevo de ROVI

Sí hay forma, y además es el camino correcto. La recomendación no es eliminar el trabajo hecho, sino productizarlo: mover COPIM de una experiencia de demo autónoma a un módulo institucional de ROVI con navegación, permisos, estados y servicios propios, pero reutilizando la base multi-workspace y el shell actual.

1. Decisión recomendada

La mejor decisión no es “borrar el demo”, sino convertir el demo en la primera versión del módulo. En otras palabras: mantener el trabajo visual y de flujo, pero quitarle el framing comercial de demo y reubicarlo dentro del producto como un módulo institucional de ROVI.

Lo que sí conviene hacer

  • Volver COPIM un módulo visible dentro del shell autenticado de ROVI.
  • Quitar lenguaje como “Demo interactivo”, “Listo para Mario” y “flujo de demo”.
  • Convertir la página actual en una experiencia de trabajo institucional.

Lo que no conviene hacer

  • No crear una app paralela.
  • No dejarlo para siempre como un micrositio público suelto.
  • No forzar desde ya todo el backend final antes de validar el módulo.

Tesis del plan

COPIM debe pasar de ser una pantalla “para vender una idea” a una superficie “que ya parece producto”. Eso se logra integrándolo al shell principal, a la navegación principal y a una capa de datos/servicios propia.

2. Qué significa “módulo COPIM”

Un módulo COPIM real dentro de ROVI no es solo una ruta. Es una combinación de navegación, permisos, estructura de datos, componentes y servicios dedicada a operación institucional.

Navegación

Entrada fija en sidebar o workspace switcher con subrutas institucionales.

Shell

Renderiza dentro del layout autenticado de ROVI, no como landing aislada.

Servicios

Usa una capa de datos propia para asociaciones, socios, membresías y eventos.

Permisos

Visible según modo, workspace o feature flag, no solo por una URL pública.

Data sembrada dentro de una sola página Servicios y estado por dominio Separar config, data y acciones

Lenguaje comercial Lenguaje operativo Más institución, menos pitch

3. Cambios de UX y narrativa

El primer salto de “demo” a “módulo” es visual y semántico. Antes de tocar backend pesado, hay que hacer que COPIM se sienta como una parte de ROVI y no como una pieza especial montada para vender.

Quitar

  • `Demo interactivo`
  • `Listo para Mario`
  • `Ver flujo de demo`
  • Hero con tono de pitch comercial

Poner

  • Header institucional más sobrio
  • Contexto de workspace: COPIM / Asociación / Socio
  • Breadcrumb o nombre del módulo
  • KPIs, cola operativa, actividad y acciones reales

La señal más fuerte de que COPIM ya es módulo no es una tabla nueva. Es que deja de hablar como demo y empieza a hablar como producto.

4. Arquitectura propuesta

La forma correcta de incorporarlo es convertir COPIM en un módulo dentro del app shell, con sus propios componentes, config y servicio, sin depender de una sola página gigante.

Capa 1 · Routing

  • Rutas de producto bajo ` /copim/* `
  • Protección condicional por feature flag o modo
  • Fallback a overview institucional

Capa 2 · Module shell

  • `CopimModulePage` o `CopimWorkspacePage`
  • Header institucional
  • Subnav interna
  • Contexto de rol / asociación / workspace

Capa 3 · Data/service

  • `copimService.js` o hooks dedicados
  • Asociaciones, socios, renovaciones, eventos
  • Fuente mock primero, API después

Sidebar.js Selector de perfil + nav general Entrada estable a módulo institucional

5. Qué necesita backend

Para que COPIM se quede ya como módulo serio, no todo el backend tiene que estar listo desde el día 1, pero sí conviene preparar el modelo correcto.

Mínimo backend para productizar

  • Feature flag de acceso a módulo COPIM.
  • Contexto de perfil o modo institucional.
  • Endpoints mock o seed para asociaciones, socios y renovaciones.

Backend completo posterior

  • Nuevos `tenant_type`: `association`, `council`.
  • `persona_type` en memberships.
  • Capabilities por módulo en vez de solo `account_type`.
Modelo recomendado de evolución

Fase rápida: dejarlo como módulo de frontend con fuente mock controlada.

Fase productiva: conectar a workspaces reales y a un backend institucional.

Fase escalable: mover permisos a capabilities y soportar COPIM nacional + asociaciones + socio dentro del mismo stack.

6. Fases de implementación

El plan correcto es migrar por capas, no rehacer todo a la vez.

Fase Objetivo Resultado Tiempo
Fase 1 Desdemo-izar COPIM Quitar copy demo, reordenar header, dejarlo con tono de módulo 2-3 días
Fase 2 Integrarlo al shell de ROVI Entrada estable en sidebar y navegación institucional interna 2-4 días
Fase 3 Separar componentes y servicios Módulo mantenible con `copimService` y componentes propios 4-6 días
Fase 4 Conectar datos y permisos reales Módulo listo para piloto interno / cliente 1-2 semanas

Orden recomendado

  • Primero producto visual.
  • Luego estructura técnica.
  • Después datos reales y permisos.

7. Backlog por archivo / frente

Esto es lo que habría que hacer de forma concreta para convertirlo de verdad en módulo.

Frontend product

  • Crear `CopimModulePage` como versión productizada del actual demo.
  • Extraer bloques: header, stat cards, roster, memberships, events, intelligence.
  • Reescribir copy y labels institucionales.

Routing & navigation

  • Definir `COPIM` como módulo principal dentro del sidebar.
  • Agregar subrutas y navegación persistente.
  • Ocultar o degradar la ruta pública demo a uso comercial secundario.

Service layer

  • Crear `copimService.js`.
  • Separar datasets mock de la página.
  • Preparar hooks tipo `useCopimOverview`, `useCopimMembers`, `useCopimEvents`.

Backend / permissions

  • Feature flag institucional por usuario o workspace.
  • Preparar endpoint `me` enriquecido con modo o capabilities.
  • Planear evolución a `tenant_type` y `persona_type`.

8. Criterios de éxito

El módulo estará bien integrado cuando cumpla estas señales.

Se ve nativo

No parece landing ni demo. Parece una parte legítima del producto.

Se navega como producto

El usuario entra, cambia de sección y entiende el modelo institucional sin explicación extra.

Se puede evolucionar

La base técnica ya permite sustituir mocks por APIs reales sin rehacer todo.

9. Riesgos y mitigación

El riesgo no es técnico solamente. También es de posicionamiento de producto.

Riesgo 1

Quedarse a medio camino: que COPIM siga oliendo a demo aunque viva en ROVI.

Mitigación: cambiar copy, header, navegación y framing primero.

Riesgo 2

Acoplarlo a una sola página gigante: difícil de mantener.

Mitigación: extraer componentes y servicios antes de crecer más.

Riesgo 3

Meter backend final demasiado pronto: mucho esfuerzo antes de validar producto.

Mitigación: usar fuente mock controlada y migración gradual.

Riesgo 4

Separarlo demasiado de ROVI: perder reutilización del stack existente.

Mitigación: mantener shell, auth, sidebar y workspaces como base.

Conclusión operativa

Sí hay forma de dejar de mostrar COPIM como demo y convertirlo en un módulo nuevo de ROVI. De hecho, ese es el siguiente paso correcto: productizar la experiencia actual, integrarla al shell real y luego ir sustituyendo lo mock por datos y permisos institucionales.
