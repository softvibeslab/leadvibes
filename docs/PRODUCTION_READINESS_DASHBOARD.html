Resumen Ejecutivo

El proyecto ya tiene forma real de producto: auth, leads, dashboard, importación, settings, landing pública, Docker y documentación operativa. La base es suficientemente madura para preparar un MVP, pero todavía no conviene llamarlo “production-ready” sin un cierre técnico corto.

Fortalezas

Base de producto sí existe

Backend FastAPI amplio, frontend React con múltiples pantallas, proxy Nginx, compose files, despliegues GitHub Actions y documentación de go-live ya presentes en el repo.

Lectura realista

MVP sí, productivo pleno aún no

Hay huecos de integración, drift entre deploy y compose, dependencia de variables de build en frontend y endpoints no alineados entre UI y API.

Semáforo General

Salida recomendada

Lanzar una primera versión con alcance controlado: auth + dashboard + leads + import + landing + settings (+ calendario si se valida). Dejar campañas, automatizaciones avanzadas y analítica profunda fuera del mensaje comercial inicial.

Decisión de Go-Live

Estado recomendado para la decisión ejecutiva.

Condicional ¿Subir a VPS hoy? Sí, pero solo después de una ronda corta de hardening técnico y smoke tests reales.
Sí ¿Hay base suficiente para MVP? Sí. El producto ya cubre el flujo central de CRM y onboarding operativo.
No ¿Está listo para vender todo el catálogo? No. Campaigns, automations y parte de analytics todavía muestran señales de demo/parcial.
Ruta recomendada Estrategia Corregir P0/P1, desplegar preview estable, validar smoke, luego promover a producción.

Bloqueos Críticos

Puntos que sí pueden romper una salida a VPS si no se corrigen.

1. Endpoint roto en broker landing

El frontend llama /api/landing/broker-launch pero el backend expone /api/landing/lead.

2. URL duplicada en database chat

La página usa api.post('/api/database-chat') aunque el cliente ya lleva base /api.

3. Frontend dependiente de env build-time

Import, email editor y automations pueden fallar si REACT_APP_BACKEND_URL no está presente en build.

4. Deploy workflow y compose desalineados

GitHub Actions hace pull de imágenes GHCR, pero el compose de Hostinger está definido con build:.

5. Riesgo de secretos / configuración

.env está trackeado y hay fallback inseguro para JWT si falta secreto real.

Infraestructura y Deploy

Lo bueno y lo pendiente en la capa operativa.

Lo que sí suma

Base operativa presente

Existen docker-compose.yml, compose de Hostinger, preview y dev, Dockerfiles de backend/frontend, Nginx de frontend y workflows de deploy para production, dev y preview.

Lo que falta cerrar

Camino de deploy unificado

Hace falta decidir una sola estrategia: build en servidor o imágenes preconstruidas en GHCR. Ahora mismo coexisten ambas y eso mete riesgo.

Riesgo operativo

Smoke test local no verificado en este entorno

La suite no pudo ejecutarse aquí porque faltan pytest y yarn. El análisis es fuerte a nivel de código y configuración, pero antes del go-live hay que ejecutar pruebas reales en preview o en un VPS de staging.

Seguridad y Config

Riesgos que no deben salir tal cual a producción.

Tema Estado Acción
`.env` versionado Riesgo alto Quitar de git, rotar secretos y reemplazar por plantilla.
JWT fallback Riesgo alto Eliminar secreto por defecto y fallar si falta variable real.
Expiración JWT inconsistente Riesgo medio Unificar minutos/horas en compose, backend y docs.
CORS y dominios Riesgo medio Normalizar URLs finales de producción y preview.
HTTPS Pendiente Configurar Certbot o reverse proxy final antes de exponer público.

Plan Recomendado de Salida

Secuencia sugerida para pasar de repositorio a VPS productivo sin improvisar.

Fase 1. Hardening técnico Corregir endpoints rotos, rutas API relativas, variables de entorno, JWT y estrategia de deploy.
Fase 2. Preview estable Levantar entorno preview y validar login, create lead, pipeline, importación, landing y health checks.
Fase 3. Producción MVP Publicar únicamente el alcance comercial realmente cubierto por el producto.
Fase 4. Módulos fase 2 Campaigns, analytics avanzado y automations reales una vez estabilizado el core.

Checklist de Aprobación

Condiciones mínimas para considerar “apto para subir”.

Corregir broker landing Corregir database chat Blindar URLs frontend Sacar `.env` del repo Unificar CI/CD y compose Ejecutar smoke test en preview Validar login y pipeline Validar importación Definir alcance MVP comercial
